# AI 实施检查清单

在实施 OpenSpec 变更时，AI Agent 应该在以下关键节点进行自我检查。

## 📋 开始实施前

### 理解阶段
- [ ] 已读 `proposal.md`，理解**为什么**要做这个变更
- [ ] 已读 `design.md`（如存在），理解**如何**实现
- [ ] 已读 `tasks.md`，理解**做什么**
- [ ] 已检查 `openspec/specs/` 中的相关能力规范

### 依赖检查
- [ ] 检查 `openspec/changes/` 是否有冲突的变更
- [ ] 检查相关文件的最近修改历史
- [ ] 确认开发环境可以编译通过

### 任务质量评估
- [ ] 所有任务都有明确的验收标准？
  - 如果没有 → 停止，要求补充
- [ ] 关键测试都是"必需"而非"可选"？
  - 如果有"可选"的集成测试 → 质疑合理性
- [ ] 任务分解是否合理（每个 <100 行代码）？
  - 如果太大 → 建议拆分

## 🔨 实施每个任务时

### 任务开始前
- [ ] 明确任务的验收标准
- [ ] 理解如何验证任务完成
- [ ] 确认需要修改哪些文件

### 编码阶段
- [ ] 代码实现符合 design.md 的设计
- [ ] API 使用方式正确（查文档/示例）
- [ ] 错误处理路径已实现
- [ ] 日志输出已添加（INFO/DEBUG/WARNING/ERROR）

### 验证阶段（关键！）
- [ ] **编译通过**（`ninja` 或 `make`）
- [ ] **警告已处理**（修复或解释）
- [ ] **验收条件已满足**（逐条检查）
  - 如果验收条件不可验证 → 这是任务定义问题，需反馈
- [ ] **日志已验证**（如果任务涉及运行时行为）
  - grep 相关日志关键字
  - 确认日志格式、级别、内容正确

### 常见陷阱检查
- [ ] 内存管理：所有权是否清晰？
  - 谁创建？谁销毁？
  - 是否需要 Copy 而非共享指针？
- [ ] API 使用：是否查看了源码或文档？
  - 特别注意返回值含义
  - 注意前置条件（如 `Copy()` 要求 buffer 为空）
- [ ] 开关控制：功能是否可以独立开启/关闭？
  - 避免多个功能共用一个开关
  - 检查是否影响其他功能
- [ ] UI 状态：用户界面是否同步更新？
  - 按钮文本、可用性
  - 状态指示器

### 标记完成前
- [ ] **所有**验收条件都满足（不是"大部分"）
- [ ] **没有**遗留 TODO/FIXME（或已创建跟踪任务）
- [ ] **代码已提交**（如果分步提交）

## 🧪 测试任务实施

### 测试任务不可跳过！
- [ ] **单元测试**：即使是"简单"功能，也要验证边界条件
- [ ] **集成测试**：端到端验证功能在真实场景下工作
- [ ] **回归测试**：确认没有破坏现有功能

### 测试实施检查
- [ ] 测试用例覆盖成功和失败路径
- [ ] 边界条件已测试（null、空、极端值）
- [ ] 测试结果已记录（日志、截图、输出文件）
- [ ] 如果测试失败 → 修复代码，重新测试

### 测试标记为"可选"时
- [ ] 质疑是否真的可选
- [ ] 如果是性能测试、压力测试 → 可能可选
- [ ] 如果是功能验证 → **不可选**

## 📝 文档任务实施

### 文档完整性
- [ ] API 文档已更新（如果有新接口）
- [ ] 使用示例已提供
- [ ] 使用示例**已验证**（复制代码能运行）
- [ ] 已知限制已记录

### 文档质量
- [ ] 技术术语准确
- [ ] 代码示例格式正确
- [ ] 无拼写/语法错误
- [ ] 中英文混排格式规范

## 🎯 变更完成前（整体检查）

### 功能完整性
- [ ] 所有 tasks.md 任务都完成
- [ ] 所有验收条件都满足
- [ ] 功能在真实场景下工作（不只是单元测试）

### 代码质量
- [ ] 编译干净（0 errors, 0 warnings 或已解释）
- [ ] 代码风格一致
- [ ] 注释清晰（特别是复杂逻辑、陷阱）
- [ ] 无明显性能问题

### 用户体验
- [ ] UI 操作流畅、符合预期
- [ ] 错误提示友好、可操作
- [ ] 功能开关独立、清晰
- [ ] 无意外副作用

### 集成验证
- [ ] 与现有功能配合正常
- [ ] 回归测试通过
- [ ] 相关文档已更新

## 🚨 出现以下情况时，立即停止并反馈

### 设计问题
- [ ] 发现 design.md 中的设计有缺陷
- [ ] API 使用方式与设计不符
- [ ] 需要额外的模块/接口未在设计中

**行动**：更新 design.md，重新评估 tasks.md

### 需求遗漏
- [ ] 发现缺少关键功能（如开关控制）
- [ ] 用户体验有明显问题
- [ ] 与现有功能冲突

**行动**：更新 proposal.md 和 tasks.md

### 任务定义问题
- [ ] 任务验收标准不明确
- [ ] 任务粒度太大
- [ ] 关键测试被标记为"可选"

**行动**：重构 tasks.md

### 技术障碍
- [ ] API 不按预期工作（如 `Copy()` bug）
- [ ] 性能严重不达标
- [ ] 内存管理有风险

**行动**：调研替代方案，更新 design.md

## 💡 质量自检公式

```
任务完成 = 代码实现 ✅
          + 编译通过 ✅
          + 验收满足 ✅
          + 日志验证 ✅
          + 测试通过 ✅
          + 文档更新 ✅
```

**缺少任何一项 = 任务未完成**

## 📊 实施质量评分

### A 级（优秀）
- 所有验收条件满足
- 测试覆盖充分
- 日志清晰完整
- 文档准确详细
- 无遗留问题

### B 级（良好）
- 验收条件满足
- 基本测试通过
- 日志基本完整
- 文档基本准确
- 遗留问题已记录

### C 级（及格）
- 功能基本工作
- 部分测试通过
- 有日志输出
- 有文档说明

### F 级（不合格）
- 功能不工作
- 测试未通过/未执行
- 无日志或日志错误
- 无文档

**要求：所有任务至少达到 B 级，关键任务达到 A 级**

## 🔄 本次 Bug 的反思

### Bug: `Copy()` API 误用

**如果使用此检查清单，会在哪里发现？**

✅ **实施阶段 - API 使用检查**：
```
- [ ] API 使用方式正确（查文档/示例）
```
→ 查看 `CFX_DIBitmap::Copy()` 源码会发现：
  - Copy() 内部会调用 Create()
  - 如果 buffer_ 已存在会返回 false

✅ **验证阶段 - 验收条件检查**：
```
- [ ] `Copy()` 返回 `true`
```
→ 实际运行时发现返回 false，验收不通过

✅ **验证阶段 - 日志验证**：
```
- [ ] 日志显示 "Created internal copy"
```
→ 实际看到 "Failed to copy"，验收不通过

**结论**：如果严格遵循检查清单，这个 bug 在标记完成前就会被发现。

### Bug: 开关控制缺失

**如果使用此检查清单，会在哪里发现？**

✅ **开始前 - 任务质量评估**：
```
- [ ] 任务分解是否合理？
```
→ 发现缺少"应用层开关控制"相关任务

✅ **实施阶段 - 常见陷阱检查**：
```
- [ ] 开关控制：功能是否可以独立开启/关闭？
  - 避免多个功能共用一个开关
```
→ 发现水印和替换共用开关，有问题

✅ **完成前 - 用户体验**：
```
- [ ] 功能开关独立、清晰
```
→ 发现无法独立控制，验收不通过

**结论**：检查清单能在多个阶段发现设计遗漏。

## ⚡ 快速自检（30 秒版）

标记任务完成前，问自己 3 个问题：

1. **能用吗？** → 功能在真实场景下工作
2. **对吗？** → 所有验收条件满足
3. **好吗？** → 日志清晰、体验友好、无遗留问题

**3 个"是" → 可以标记完成**
**任何"否" → 继续改进**
