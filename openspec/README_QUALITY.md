# OpenSpec 质量改进指南

## 🎯 快速开始

### 我是 AI Agent，要实施一个变更

**第一步**：阅读 `AI_IMPLEMENTATION_CHECKLIST.md`（5 分钟）
- 了解在哪些关键点需要自检
- 理解什么叫"任务完成"

**第二步**：按照清单实施
- 开始前检查任务质量
- 实施时验证验收条件
- 完成前运行完整性检查

**第三步**：标记完成
- 只有当所有验收条件满足时
- 不是"差不多"，是"完全满足"

### 我是人类，要创建任务清单

**参考**：`templates/task_with_acceptance.md`

**核心原则**：
1. 每个任务有明确的验收标准
2. 验收标准可验证（不是"实现得好"，是"日志显示 X"）
3. 测试任务不能标记为"可选"

**模板**：
```markdown
- [ ] 1.1 任务描述
  - **实现**：具体实现方法
  - **验收**：
    - [ ] 可验证的条件 1
    - [ ] 可验证的条件 2
  - **测试**：如何测试
```

### 我要了解为什么需要这些改进

**阅读**：`OPENSPEC_IMPROVEMENT_PROPOSAL.md`

**TL;DR**：
- 之前：任务完成 = 代码写完 + 编译通过
- 现在：任务完成 = 代码 + 编译 + 验收 + 日志 + 测试
- 原因：发现了 2 个严重 bug，都是因为"完成"标准太低

### 我想看改进效果总结

**阅读**：`QUALITY_IMPROVEMENTS_SUMMARY.md`

**关键数据**：
- 首次实现正确率：70% → 95%
- 用户发现 bug：高 → 低
- Bug 发现时间：用户使用后 → 实施阶段

## 🔍 核心改进点

### 1. 验收驱动实施（Acceptance-Driven Implementation）

**改进前**：
```
写代码 → 编译 → ✅ 完成
```

**改进后**：
```
理解验收标准 → 写代码 → 编译 → 验证验收 → ✅ 完成
```

**关键**：标记完成前必须验证功能真的工作。

### 2. 测试不可选（Mandatory Testing）

**改进前**：
```markdown
- [ ] 5.5 编写单元测试（可选）
- [ ] 5.6 测试实际替换（需要应用层实现）
```
→ 结果：都被跳过，bug 未被发现

**改进后**：
```markdown
### 单元测试（必需）
- [ ] 5.1 测试 API 不同返回值

### 集成测试（必需）
- [ ] 5.2 端到端测试真实场景

### 回归测试（必需）
- [ ] 5.3 验证现有功能不受影响
```
→ 都是必需，必须完成

### 3. 任务质量检查（Task Quality Check）

**改进前**：
```markdown
- [ ] 2.3 创建内部副本
```
→ 不知道怎么验证"创建成功"

**改进后**：
```markdown
- [ ] 2.3 创建替换图片的内部副本
  - **实现**：`internal_copy->Copy(replacement)`
  - **验收**：
    - [ ] Copy() 返回 true
    - [ ] 日志显示 "Created internal copy at 0x..."
    - [ ] 内存地址与外部不同
  - **测试**：不同尺寸图片
  - **注意**：不要先 Create()，Copy() 会自动处理
```
→ 明确实现方法、验收标准、测试方法、常见陷阱

## 💡 常见问题

### Q: 这会不会让实施变慢？

A: **短期慢，长期快**
- 短期：多了验证步骤（+20% 时间）
- 长期：少了返工时间（-50% bug）
- 总体：减少了用户发现 bug 后的昂贵修复

### Q: 所有任务都需要这么详细吗？

A: **看复杂度**
- 简单任务（<10 行）：简化验收即可
- 中等任务（<100 行）：标准验收
- 复杂任务（>100 行）：详细验收 + 子任务

### Q: 如果任务没有验收标准怎么办？

A: **停止并反馈**
1. 不要盲目实施
2. 建议补充验收标准
3. 等待任务更新后再实施

### Q: 验收条件不可验证怎么办？

A: **重新定义**
- ❌ "实现得好" → 不可验证
- ✅ "日志显示成功消息" → 可验证
- ✅ "测试用例通过" → 可验证

### Q: 集成测试太麻烦可以跳过吗？

A: **绝对不行**
- 单元测试只验证部分逻辑
- 集成测试验证整体功能
- 本次 bug 只有集成测试能发现

## 🎓 学习案例

### 案例：本次的 `Copy()` Bug

**如果使用旧流程**：
```
1. 写代码：internal_copy->Create() + Copy()
2. 编译通过 ✅
3. 标记完成 ✅
4. 用户使用 → 发现不工作 ❌
5. 返工修复
```

**如果使用新流程**：
```
1. 理解验收：Copy() 应该返回 true
2. 写代码：internal_copy->Create() + Copy()
3. 编译通过 ✅
4. 验证验收：Copy() 返回 false ❌ → 不通过！
5. 查文档：发现 Copy() 内部会 Create()
6. 修改代码：只调用 Copy()
7. 验证验收：Copy() 返回 true ✅
8. 检查日志：看到 "Created internal copy" ✅
9. 标记完成 ✅
```

**差异**：
- 旧流程：bug 在第 4 步被用户发现
- 新流程：bug 在第 4 步被自己发现
- 结果：节省了用户时间和返工成本

### 案例：开关控制缺失

**如果使用旧流程**：
```
1. 实现图片替换 ✅
2. 实现水印叠加 ✅
3. 用户使用 → 发现无法独立控制 ❌
4. 返工添加开关
```

**如果使用新流程**：
```
1. 读 tasks.md：没有开关控制任务
2. 自检：功能应该可独立控制 ❌
3. 反馈：需要添加开关控制任务
4. 更新 tasks.md
5. 实施完整方案（包括开关）✅
```

**差异**：
- 旧流程：设计缺陷在用户使用后发现
- 新流程：设计缺陷在实施前发现
- 结果：避免了不完整的实现
