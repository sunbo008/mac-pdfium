# OpenSpec 质量改进总结

## 📊 改进背景

在实施 `add-external-image-replacement` 功能时发现的关键问题：

### Bug #1: API 误用导致功能失败
- **问题**：`Copy()` API 使用错误（先 `Create()` 再 `Copy()`）
- **影响**：图片替换完全不工作，用户看到水印叠加在原图上
- **根因**：任务标记完成但未实际验证功能

### Bug #2: 功能耦合导致体验问题
- **问题**：水印和替换共用开关，无法独立控制
- **影响**：启用替换时自动叠加水印
- **根因**：设计阶段遗漏开关控制需求

## 📁 新增资源

### 1. `AI_IMPLEMENTATION_CHECKLIST.md`
**用途**：AI Agent 实施时的自检清单

**关键检查点**：
- ✅ 编译通过
- ✅ 验收条件满足
- ✅ 日志已验证
- ✅ API 使用正确
- ✅ 开关控制独立

**使用时机**：
- 开始实施前：评估任务质量
- 实施每个任务时：验证完成度
- 标记完成前：最终检查

### 2. `templates/task_with_acceptance.md`
**用途**：如何编写高质量任务定义

**核心理念**：
- 任务要有明确的验收标准
- 验收标准必须可验证
- 测试不能标记为"可选"

**对比示例**：

❌ **不好的任务**：
```markdown
- [ ] 实现图片替换功能
- [ ] 添加错误处理
- [ ] 更新文档（可选）
```

✅ **好的任务**：
```markdown
- [ ] 1.1 在 ImageRenderer 中添加替换调用
  - **实现**：调用 `callback->GetReplacementImage()`
  - **验收**：
    - [ ] 编译通过
    - [ ] 日志显示 "Got replacement image"
    - [ ] null 返回时使用原图
  - **测试**：mock callback 返回不同值
```

### 3. `OPENSPEC_IMPROVEMENT_PROPOSAL.md`
**用途**：系统性改进提案

**核心改进**：
1. **任务定义增强**：明确实现、验收、测试
2. **测试策略强化**：单元/集成/回归，全部必需
3. **实施检查清单**：完整性自检
4. **验收驱动开发**：先写验收测试，再实现
5. **设计审查清单**：架构/内存/错误/UX

### 4. `AGENTS.md` 更新
**新增内容**：
- 质量资源引用（开头）
- 验收驱动实施流程（Stage 2）
- 关键原则强调

```
8. 运行测试 ← 新增：端到端验证

```

**优势**：
- ✅ 功能在真实场景下验证
- ✅ API 误用会被发现
- ✅ 设计遗漏会被质疑

## 💡 关键原则

### 1. 验收驱动（Acceptance-Driven）
**不要**：实现 → 标记完成
**而是**：理解验收 → 实现 → 验证验收 → 标记完成

### 2. 测试不可选（Testing is Mandatory）
**不要**：标记测试为"可选"
**而是**：集成测试必需，单元测试强烈推荐

### 3. 完整性优先（Completeness First）
**不要**：快速完成 80%
**而是**：彻底完成 100%（包括文档、测试、边界条件）

### 4. 质疑合理性（Question Everything）
**不要**：盲目执行任务
**而是**：任务质量有问题 → 停止并反馈

## 📚 使用指南

### 对于 AI Agent

**每次实施变更时**：
1. 打开 `AI_IMPLEMENTATION_CHECKLIST.md`
2. 在关键节点进行自检
3. 不满足清单要求 → 不标记完成

**创建任务时**：
1. 参考 `templates/task_with_acceptance.md`
2. 确保每个任务有验收标准
3. 确保测试任务必需而非可选

### 对于人类审查者

**审查提案时**：
1. 检查任务是否有验收标准
2. 检查测试策略是否充分
3. 检查是否遗漏关键功能（如开关控制）

**审查实施时**：
1. 要求展示验证证据（日志、测试结果）
2. 不接受"差不多就行"
3. 发现问题 → 返工而非妥协

## 🎓 经验教训

### 本次 Bug 的启示

#### 教训 #1：编译通过 ≠ 功能正确
```cpp
// 编译通过的错误代码
internal_copy->Create(...);  // ✅ 编译通过
internal_copy->Copy(...);    // ✅ 编译通过，但返回 false！
```

**启示**：必须验证返回值和运行时行为。

#### 教训 #2：任务完成 ≠ 目标达成
```markdown
- [X] 2.3 创建内部副本
```
✅ 代码已写
✅ 编译通过
❌ Copy() 返回 false
❌ 功能不工作

**启示**：完成定义必须包含验收标准。

#### 教训 #3：功能实现 ≠ 完整方案
- ✅ 图片替换逻辑实现
- ✅ 水印叠加逻辑实现
- ❌ 开关控制逻辑缺失

**启示**：要从用户角度考虑完整体验。

### 如果使用新流程

#### Bug #1 会在哪里被发现？
```
✅ 实施阶段 - API 使用检查
   → 查看 Copy() 源码发现前置条件

✅ 验证阶段 - 验收条件检查
   → Copy() 返回 false，不满足验收

✅ 验证阶段 - 日志验证
   → 看到 "Failed to copy"，不符合预期
```

#### Bug #2 会在哪里被发现？
```
✅ 开始前 - 任务质量评估
   → 发现缺少开关控制任务

✅ 实施阶段 - 常见陷阱检查
   → 发现功能耦合问题

✅ 完成前 - 用户体验检查
   → 发现无法独立控制功能
```
