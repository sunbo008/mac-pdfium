# 项目文档规范

## 核心原则

**一个功能，一个文档。**

## 文档组织规则

### 1. 文档位置

- **功能文档**：统一放在 `docs/` 目录下
- **模块简介**：可以在模块目录下放置简短的 README
- **项目根目录**：只放置项目级别的 README

### 2. 命名规范

- 功能文档命名格式：`功能名.md`（例如：`logger.md`）
- 使用小写字母和连字符
- 避免使用冗长的名称

### 3. 文档结构

每个功能文档应包含（但不限于）：

```markdown
# 功能名称

## 目录
- 快速开始
- 核心功能
- API 参考
- 使用示例
- 配置说明
- 常见问题

## 快速开始
（最重要的部分，让用户快速上手）

## 核心功能
（功能特性说明）

## API 参考
（详细的 API 文档）

## 使用示例
（实际使用案例）

## 配置说明
（配置选项和环境说明）

## 常见问题
（FAQ）
```

### 4. 文档数量限制

- ✅ **允许**：每个功能在 `docs/` 目录下有 **1 个** 主文档
- ✅ **允许**：模块目录下有 1 个简短的 README（指向主文档）
- ❌ **禁止**：将一个功能的文档拆分成多个文件
- ❌ **禁止**：创建过多的辅助文档（如 quickstart, guide, design 等）

### 5. 示例

#### ✅ 好的做法

```
docs/
├── logger.md           # 日志功能的完整文档
├── render.md           # 渲染功能的完整文档
└── export.md           # 导出功能的完整文档

platform/shared/
└── LOGGER_README.md    # 简短介绍，指向 docs/logger.md
```

#### ❌ 不好的做法

```
docs/
├── logger-quickstart.md
├── logger-usage.md
├── logger-integration.md
├── logger-design.md
├── logger-api.md
└── logger-faq.md

（太多分散的文档！）
```

## 编写指南

### 1. 内容组织

- 使用目录导航
- 从简单到复杂
- 快速开始部分最重要
- 提供完整的示例代码

### 2. 代码示例

- 示例要完整可运行
- 添加必要的注释
- 展示常见用例

### 3. 保持更新

- 功能变更时同步更新文档
- 只维护一个文档，减少维护成本

## 检查清单

在创建文档前检查：

- [ ] 是否已存在相关文档？
- [ ] 是否可以合并到现有文档？
- [ ] 文档是否放在正确的位置？
- [ ] 文档名称是否简洁明了？
- [ ] 是否包含快速开始部分？

## 违规处理

发现违反规则的文档：

1. 合并到单一文档
2. 删除冗余文档
3. 更新引用链接
